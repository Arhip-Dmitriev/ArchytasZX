ARCHYTASZX DOCUMENTATION
========================

The Benchmark Suite, Version 2

Applies to: ArchytasZX 2.0.x
Implementation: benchmarks/ (python -m benchmarks), archytaszx/trace.py (timing spans)


1. PURPOSE
----------

The suite measures how far, how fast and with how large a proof the engine settles the
equations "circuit = what the circuit is supposed to do", true ones (the set S) and adversarial
false ones (the set F), against the tools a user would otherwise reach for. It reports
quantities: times, counts, sizes and rates. Pass/fail checks of the suite are tests (section
13). Every ArchytasZX result comes from symbolic rewriting; the numeric oracle enters only where
the engine itself uses it. Rival tools run as their users run them, simulators included.

Everything that defines a run comes from one file, benchmarks/config.toml; every value can be
overridden on the command line with --set KEY=VALUE, and every run is keyed by the hash of the
resolved configuration (section 10).


2. TERMS
--------

  Term         Meaning
  -----------  ---------------------------------------------------------------------------
  equation     a pair of diagrams claimed equal: the naive circuit and the specification
  subject      a named algorithm, code, protocol or circuit; it gives one or more equations
  S, F         the true equations; one false equation per equation of S
  version      symbolic (n and d letters), concrete (n and d numbers), restricted (a claim
               limited by engine clauses)
  point        one concrete (n, d) of one equation
  run          one tool on one point (or the symbolic version), in a fresh process
  stage        one timed part of a run: generate, decide, certificate, lean_export, lean_check
               (ArchytasZX); prepare and check (rivals)
  unit         one (equation, tool): its symbolic run, phase 1 ladder and phase 2 fill
  K            the successful points each unit aims for (default 16)


3. THE SUBJECT CATALOGUE
------------------------

Implementation: benchmarks/subject.py, benchmarks/subjects/*.py, benchmarks/ir.py,

3.1 Subject files

One Python file per subject in benchmarks/subjects/ defines SUBJECT, a Subject:

  Field           Meaning
  --------------  -------------------------------------------------------------------------
  id, name        identity; id equals the file name
  category        algorithm, code, protocol or circuit
  source          a key of public_publications/references/REFERENCES.bib or a
                  citation
  size_parameter  what n counts (qudits, code distance, ...), or None for a fixed size
  dimension       "general" (any d in the domain) or a fixed int (2 for qubit subjects)
  domain          Domain(n_min, n_max, n_step, d_min, d_max, d_condition), the condition one
                  of any, ge2, prime, odd, odd_prime, even
  equations       Equation(key, circuit, specification, form, reference, literal)
  restricted      tuples of engine clauses (n = v, n >= c, n = a*m + c, d = v, d >= c); each
                  tuple is an equation of its own, with its own F partner
  clifford, note  a flag and a remark, not read by the suite

An Equation's circuit maps (n, d) to an IR circuit; its specification maps a SpecContext to a
ZXW diagram body in the engine's DSL, written from the definition and independent of the
circuit. form says how n enters: boxed (a register count, so the symbolic version exists),
unrolled (one wire per qudit, concrete n only) or fixed. literal writes every dimension as a
literal (phase tables need it). reference, when given, is a gate-level IR circuit realising
the specification (a textbook alternative: a CX ladder for a fan, the plain gate for a gate
identity); tools that compare two circuits use it. Without one, QCEC uses the specification as
one dense Unitary or Prepare gate (benchmarks/tools/rival.py, reference_circuit); Feynman, DiZX
and AutoQ need an explicit reference. Test 1 checks every reference against the specification.

3.2 The circuit IR

Wires are names; a register is a name with a count (int or symbol), and a gate naming a register
acts on every copy. Gates: Init, Post, Discard, Measure; X^a (|k> -> |k+a>), Z^a
(|k> -> w^(ak)|k>), F^p; ZPhase and XPhase (phase entries or a rule in k); CX and CZ (s = +1 or
-1); Swap; PhaseFn (a diagonal phase function of several wires, optionally with its support, the
only inputs where it may be nonzero, so the translator evaluates just those); MCX and MCZ (controls on given
values); Perm (a permutation of the joint basis); Oracle (|x, y> -> |x, y + f(x)>). A
classically controlled correction is a CX or CZ from a measured wire. Amounts and rules are
sympy expressions in d, n and k. Two loop gates: Chain(count, body, carries, index) runs body
once per copy m of the registers of that count (index read as m), and after each copy every
(carry, register) pair exchanges values, so the register's copy keeps the carry's value and the
single carry wire goes on with the register's; Pairs(over, body, index, pair_index) runs body
on the wires "left" (copy j) and "right" (copy k) of register over for every j < k;
Tree(count, body, parent, children, level, position) runs body once per copy c(L, P) of a tree
of depth count on its parent value as wire parent and on fresh local wires, the children
wires' final values feeding c(L + 1, b P + i) and the leaves' children taking parent's place in
the boundary, leaf-major. tools/common.expand unrolls all three at a concrete count, and the
dense reference evaluates that.

3.3 The naive translator

translate.translate turns an IR circuit into a DSL body, one generator group per gate, every node
named and every wire explicit, no simplification, deterministic output. Encodings (D the wire
dimension):

  Gate          Diagram                                                   Scalar
  ------------  --------------------------------------------------------  ---------
  Init v        X(0 -> 1) phase{k: -v k/D}                                D^(-1/2)
  Post v        X(1 -> 0) phase{k: v k/D}                                 D^(-1/2)
  Discard       G(1 -> 0)
  Measure       Z(1 -> 2), second output to G
  X a, Z a      X(1 -> 1) phase{k: -a k/D}, Z(1 -> 1) phase{k: a k/D}
  F p           p mod 4 F nodes
  CX s          Z(1 -> 2) on c, X(2 -> 1) on t, joined (F F when s = -1)    D^(1/2)
  CZ s          Z(1 -> 2) on c, Z(2 -> 1) on t, joined by F (F^3 when -1)   D^(1/2)
  PhaseFn       binders to one leg, Z with the phase table, splitters       e^(2 pi i f(0))
                back; the phase at index 0 moves to the scalar
  MCZ, MCX      PhaseFn on controls and target (MCX between F and F^3)
  Oracle        F, PhaseFn f(x) y / D, F^3 on y
  Perm          fresh Z(0 -> 1) leg t, PhaseFn -t p(x)/D on (t, x),          D^(-1/2)
                Z(1 -> 0) on x, F on t

A register's gates go in one node-scope box per count; a gate between a register and a single
wire leaves the single wire's spider outside the box, where it takes one leg per copy. A Chain
is one named chain box (repeat COUNT as NAME [index I]) over its body's nodes, linked from each
carry's end after the exchange to the first port the carry entered in the copy (chain NAME:
p -> q); a carry or register with no node in the copy gets an identity Z(1 -> 1). Pairs puts
Z(2 -> 1) (in1 the right port) then Z(1 -> 2) (out1 the left port) on the register's wire in
the register's box, which takes the index, and the CZ's F nodes in a pair box with copy scalar
D^(1/2). A chain's registers are used only inside it. A Tree is one named tree box (tree NAME:
q <- p_1, ..., p_b) over its body's nodes, q the first port the parent entered in the copy and
p_i the children wires' ends, its scalar factors as the box's copy scalar; the parent wire's
output is the run of p_i, and no gate follows on it. Phase
tables, multi-controlled gates, oracles and permutations need literal concrete dimensions; the
symbolic version of such an equation is unsupported and recorded as such.

3.4 The engine script

subject.script builds, for one equation at one version,

    @rhs =
        dim d [= V]          (general d, not literal)
        count n [= V]        (boxed n)
        SPECIFICATION
    load
        dim d [= V]
        count n [= V]
        NAIVE CIRCUIT
    decide against @rhs [for CLAUSES]

A concrete point binds the numerals as a user writing numbers does; the engine abstracts them
on entry (ENGINE_COMMANDS.txt, section 3), so a decide line without a clause decides the family.
A concrete version's claim is its point, so its decide line carries the point clauses after any
restriction clauses: d = V for a general d not written literally, n = V for a boxed count
(subject._point_clauses; Script.point_claim, generate's point_claim). Literal dimensions and
unrolled counts are instances already. The symbolic version keeps no point clause.

3.6 Coverage rule

The catalogue is the set the following rule defines; every family it lists is met.

Scope. A subject is a finite-dimensional gate-model claim (gates, preparations, measurements,
post-selection, discards) with an exact closed-form specification. Out of scope: continuous-
variable and bosonic systems (GKP, cat and binomial codes, boson sampling), analog, adiabatic
and annealing computation, claims that hold only approximately (product-formula error bounds,
approximated rotations, polynomial approximations by signal processing), non-additive and
approximate codes, sampling experiments without a closed-form output (random circuit
sampling), and circuits whose rotation angles are not rational turns, which the phase language
does not hold (Dicke states D^n_k beyond power-of-two splits, exact Grover search away from
N = 4).

Rule. The catalogue holds at least one subject for every family below and one subject for every
algorithm, protocol, construction or code named in it; codes are represented by one member of
each stabilizer-code family. The families follow the divisions of the standard surveys; the
named members are the ones those divisions are illustrated by.

colour-0 checks; the holographic code is the stabilizer group of the contracted network on its
open legs.


4. THE FALSE SET
----------------

Implementation: benchmarks/breaks.py; generated into results/false_set.json
(runner.false_set: shard 0 generates it under a lock on results/false_set.lock, through a
per-task temporary file; every other shard waits until the file holds the config's set).

Every S equation gets one false partner: one break applied to its circuit IR (the specification
is never edited, so every tool sees the same pair). The kind is picked per equation by the
assignment rule (round_robin from the equation's index, or a seeded shuffle); a kind with no
variant that yields a witness is skipped for the next. Each F record stores the edit, a witness
(a point, output and input indices, both values; for a mixed equation, indices of the doubled
diagram, both sides doubled when either is mixed) and where the pair stays equal.

  Kind                    Edit                                              Equal where
  ----------------------  ------------------------------------------------  -------------------
  beyond_oracle           phase k (d-1)(d-2)(d-3)(d-4)/d, or a C(n,4)/d      the oracle grid
                          phase on a boxed equation, on an output wire       (d <= 4, n <= 3)
  beyond_N                unrolled: X on an output when n > N; boxed: a      n <= N
                          counting gadget of dimension N + 2 giving -1 at
                          n = N + 1 (mod N + 2); rivals see the same sign
  prime_only              phase (k^d - k)/d                                  prime d (and the
                                                                             Carmichael numbers)
  qubit_only              the antipode F^2 on an output                      d <= 2
  coincident_dims         phase k (D1 - D2)/D1                               D1 = D2
  scalar_small_one        scalar 1 + (d-1)(d-2)(d-3)(d-4), or 1 + n..(n-3)   the oracle grid
  global_phase            scalar e^(2 pi i/7)                                up to a global phase
  tiny_phase              phase 1/d^k (k = tiny_k) at index 1               nowhere
  leg_order               a swap of two wires of one register copy, or of    nowhere
                          the last two outputs
  box_boundary            scalar 1 + 0^(n - n_min)                           n > n_min
  state_not_map           Z at the start of an input wire                    on input 0
  single_entry            a phase table: -1 where every unmeasured single    elsewhere
                          output is 1 (no variant when none is left)
  wrong_phase             one phase or amount changed                        nowhere
  missing_gate            one gate dropped                                   nowhere
  extra_gate              X appended on an output                            nowhere
  swapped_control_target  one CX reversed                                    nowhere
  off_by_one_n            the circuit at n + 1                               nowhere
  wrong_dimension         one wire's dimension + 1                           nowhere

Witnesses are found densely when the tensor has at most 2^18 entries, else by plugging basis
states and effects into the closed diagram (nodes of at most 12 legs) or by symbolic contraction
at the bound values. The boxed beyond_N witness is factored: a nonzero specification entry e at
n = N + 1 (symbolic contraction) and the gadget's value g there, the broken entry being g e (on a
mixed equation, doubled entries and |g|^2, so the sign alone is no witness); the
gadget's closed form is tested at N = 1, 2, 3 (section 13). Each witness records proportional:
whether the pair differs only by a scalar at the witness point (true when the dense tensors are
one scalar times each other, and for the factored witness; false for an interface difference;
null when the witness was found without the dense tensors). F has the same three versions as S.
Kinds tiny_phase and single_entry raise the F equation's d floor to 2.

The search is bounded in time: one probe (one point of one variant) gets
false_set.probe_seconds, and an overrun counts as no witness at that point; one equation gets
false_set.equation_seconds over all its kinds, and an overrun ends the search with no F partner,
recorded with reason "time budget"; an equation whose every probe overflows the oracle's
contraction cap has none either, with reason "oracle size". The large fixed codes golay_code,
tesseract_code and polynomial_code have no F partner. On an unrolled equation a break that names
a wire records its role (open outputs, inputs, all wires) and position, and is applied to the
wire in that position at each n. Test 2 reports both reasons, and oracle-size overflows of its
equal-where checks, as SKIP lines.


5. POINTS
---------

Implementation: benchmarks/points.py

Each unit has its own seed, derived from (points.seed, equation, tool). A draw takes u uniform
on [0, 1) independently for n and d: d = floor((d_max + 1)^u), n = floor((n_max + 1)^u) - 1;
out-of-domain values are redrawn; an axis the subject lacks is held at its fixed value.

Phase 1, the ladder: step k = 1..K at n_k = floor((n_max + 1)^(k/K)) - 1 and
d_k = floor((d_max + 1)^(k/K)), clamped to the range, moved up to the nearest domain point and,
when already used, to the next unused one (n raised first, then d). Steps run in order; the
first failure (timeout, error, out of memory, wrong or unknown result, unsupported) ends the
ladder and is recorded; a harness_error, an invalid_point or a run flagged point_invalid (10.6)
is neither a success nor a failure: it is recorded under the unit's skipped and the ladder goes
on.

Phase 2, the fill: draws are kept when not at least as large, in both n and d, as some failed
point, and not used before. A success counts toward K; a failure joins the failed points (a
skipped run, as in phase 1, does neither). The
fill stops at K successes, at phase2_extra_failures failures, or when the draws run out; the
last two record region_exhausted. A domain of fewer than K points is run whole.

The symbolic version is one more run outside K. A restricted equation draws from its restricted
domain.

An F equation draws only points where its pair differs (benchmarks/differs.py). Each F record
carries differs_at, [n, d, differs] by a dense check of the broken pair (both sides doubled when
either is mixed; a boundary difference only in dimension-1 legs is no difference) at the domain
points with d <= 4 and n <= 4 (n <= 12 at a fixed d), a d's line stopping at its first point
past 2^18 entries or probe_seconds, plus the witness point; breaks.annotate adds it (generation
does), and replaces a pure-against-doubled interface witness by a dense one on the doubled pair.
A tabled point is decided by the table. Elsewhere the kind's rule decides: beyond_oracle, prime_only and coincident_dims are
equal where the phase rule is an integer at every k < d (for the d rule also d = 6, 8, 12, 24;
for the Fermat rule every prime and Carmichael d); scalar_small_one and box_boundary where the
scalar factor is 1; beyond_N unrolled where n <= N, boxed except at n = N + 1 mod N + 2;
qubit_only where d <= 2. Any other kind is equal off the table where the table shows it: at
d = 1 when every tabled d = 1 point is equal, at n = 0 when every tabled n = 0 point is,
everywhere when every tabled point is (a no-op edit), beyond the largest tabled n (d) when the
last 3 tabled n (d) are equal at every tabled d (n), and at an n beyond the table whose d line
repeats with a period p (at least 3 checks) with the tabled n mod p equal. Otherwise it differs
everywhere, except a record without a table whose witness is an interface mismatch between a
boundary and the same boundary taken twice (a pure side against a doubled one), which differs
nowhere. outcomes.equal_at uses the same predicate, so a run at such a point is invalid_point. Moving a ladder step to the next
point raises n, then d, at most 4096 values each (MAX_SCAN), then takes the first differing
domain point among the first 4096 K. The domain size that selects the whole-domain schedule
counts every domain point.


6. BENCHMARKS
-------------

B1, proving S, and B2, refuting F, record per run every stage's CPU and wall seconds and peak
memory, the derivation steps, kernel inferences (per kind), certificate bytes (the text of
certificate show), Lean lines and bytes, Lean check CPU and per-declaration profiler
milliseconds, the axiom class, and the span tree (section 7); per unit, the frontier, K reached
and region_exhausted. B2 adds the counterexample point and the Lean refutation's size. A run is
successful when stage decide gives the expected verdict certified (equal for S, unequal for F;
the record's certified field). A run giving the expected verdict uncertified (equal_uncertified,
unequal_uncertified) is logged uncertified; a run giving the opposite verdict is logged wrong
when certified and wrong (uncertified) when not. Only successes count toward K. A record from
before the uncertified verdicts (no certified field) is read by aggregate.py as: equal with
certificate kernel rejected is equal_uncertified, unknown with "not reported unequal:" in its
reason is unequal_uncertified, every other verdict unchanged. An F run at a point where its pair is
equal (section 5) is excluded from every table and counted in the aggregate summary line.

B3, diagram size (benchmarks/size.py): for every successful ArchytasZX B1 run, the smallest
diagram over both sides, both normal forms and every diagram of every certificate (replayed
step by step): nodes per generator (Z, X, W, F, T, Ti, B, S, G), node- and port-scope boxes and
their deepest nesting, phase entries, weight entries, wires, self-loops, inputs, outputs and the
scalar's operation count; total = nodes + boxes + phases + weights + wires, ties broken by fewer
wires. The same counts of the naive circuit and the naive / smallest ratio are reported. PyZX
and QuiZX report vertices and edges of their reduced graph; tket reports gates and two-qubit
gates after FullPeepholeOptimise.

8. STAGES OF AN ARCHYTASZX RUN
------------------------------

Implementation: benchmarks/tools/archytaszx.py, benchmarks/stages.py

  Stage        What runs
  -----------  -----------------------------------------------------------------------------
  generate     the engine script built from the subject (translation of the circuit)
  decide       every line of the script in one fresh session, concrete axioms on
  certificate  certificate kernel: the proof object built and kernel-checked
  lean_export  certificate lean FILE
  lean_check   the Lean runner on FILE with #print axioms; class clean, unproved, opaque

Each stage has its own CPU limit (stages.timeout_seconds, default one hour), enforced by a
profiling timer that re-fires until it escapes the engine; the worker is killed after wall_factor
times the sum of its stage limits. A stage that cannot run (certificate and Lean after an
unknown or unequal_uncertified verdict) is recorded not_run. Only decide decides success; later
stages are recorded with their status.


9. STATISTICS
-------------

Implementation: benchmarks/stats.py

Laptop: exactly repeats.laptop.runs runs (3) of every successful point. Cluster: at least
min_runs (5), then until the 95 % confidence interval of the median decide CPU has half-width
within precision (5 %) of the median, or max_runs (30). The interval is the exact order-statistic
interval: the largest j with 2 P(Binomial(m, 1/2) <= j - 1) <= 1 - confidence gives
[x_(j), x_(m+1-j)]; at 95 % it exists from m = 6. Points reaching max_runs are noisy; a point is
decided by its first run, and a later failing repeat makes it unstable. Every aggregate row has
the median, quartiles, minimum, maximum, the interval, the number of runs and the raw values.


10. EXECUTION
-------------

Implementation: benchmarks/runner.py, benchmarks/worker.py, benchmarks/log.py,
benchmarks/sources.py, benchmarks/slurm.py

10.1 The runner

    python -m benchmarks run [--profile laptop|cluster] [--set KEY=VALUE ...] [--shard I/N]
                             [--only EQUATION|TOOL-GLOB ...]
    python -m benchmarks false [--set KEY=VALUE ...]      generate results/false_set.json
    python -m benchmarks list [--set KEY=VALUE ...]       the S equations, one per line,
                                                          with category and whether the
                                                          symbolic version exists

Every action also takes --config PATH, a configuration file in place of
benchmarks/config.toml.

Units run platform.jobs at a time; a unit's runs go in order. Every run is a fresh worker process
(python -m benchmarks.worker) under a memory cap of memory_fraction of the available memory
(at most the Slurm allocation) divided by the workers (a systemd scope without swap, unloaded on exit even when it failed (--collect), else a soft RLIMIT_AS, which Lean and
the Quantomatic JVM lift: they are bounded by the Lean slots and -Xmx2g). The worker announces each
stage, so a killed run records the stage it died in. The worker and every driver lift Python's
integer string conversion limit (sys.set_int_max_str_digits(0)) at start.

Each run record carries an outcome, a stage and a cause code (10.6).

10.2 Log and resume

Each finished run is appended at once, with flush and fsync, as one JSON line to
results/raw/HOST-JOB-TASK-wK.jsonl, one file per worker thread; lines are never edited. A run is
keyed by (config hash, equation and its source digest, version, tool, point, repeat, trace); the
source digest hashes the subject file, the catalogue's helper modules and data files, ir.py,
translate.py and subject.py (for an F equation also breaks.py and its F record), so adding a
subject leaves every other key unchanged and editing one re-runs only its runs. On start every log
is read and every key present is reused: the schedule replays from logged outcomes, and a unit
whose unit record exists is skipped, except a finished F unit whose unit record lacks
differs_checked and which ran a point where its pair is equal: its schedule replays under the
differs filter and writes a new unit record with differs_checked, which the index prefers. A run cut off before its line was written leaves nothing and
is re-run whole; a truncated last line is ignored. SIGINT or SIGTERM stops new runs and sends
SIGTERM to each running worker's process group (the worker kills its Lean check, whose process
group is its own), SIGKILL after 5 s; those runs are re-run on resume. Aggregates and plots come
only from the logs, from the records whose source digest matches the current sources.

10.3 Cluster (Zaratan)

    python -m benchmarks slurm [--set KEY=VALUE ...]      writes benchmarks/slurm/run.sbatch

The job array runs on the scavenger partition only, with --requeue, whole cores
(--cpus-per-task = slurm.cpus_per_task, --hint=nomultithread) and one worker per core; array
task i runs shard i of the units. Each job first runs the calibration script (GHZ, symbolic
decide) three times; its median CPU is stored with every run and in the job's environment
record, which also holds the node, CPU model, frequency governor and memory. Reports give times
scaled by the calibration beside the raw times; raw times are compared within one CPU model.

The slurm action runs at one commit: slurm.commit when set, else the head of the latest
successful CI run on dev (gh run list). A checkout with tracked local changes is refused; a
clean one elsewhere is checked out (detached) at that commit. The sbatch file names the commit
and each array task exits when the checkout is not at it or is dirty. Every run record carries
git = {commit, dirty} of the job.

Before any unit runs, a preflight imports the harness's in-process modules (numpy, sympy,
qiskit; the extra .[benchmarks], installed by setup_rivals.sh harness) and, for each enabled
tool with an installed environment, imports its PROBE modules in that environment; any failure
stops the run with the list of problems.

10.4 Memory

Lean runs in a systemd scope of its own capped at memory_fraction of the total memory, outside
the worker's scope (whose cap would evict the memory-mapped Mathlib files). At most
floor(0.85 x total memory / 7000 MiB) checks run at a time across workers (one Lean check peaks
near 6.7 GiB), between 1 and 5, per Slurm task (else per machine); BENCH_LEAN_SLOTS overrides.
Peak memory is recorded per stage.

10.5 Laptop

The same runner and log with the laptop profile; interruption and resume as in 10.2.

10.6 Outcomes, stages and causes

Implementation: benchmarks/outcomes.py (the tables OUTCOMES, STAGES, UNSUPPORTED, CAUSES and
RUNGS, and classify), benchmarks/reclassify.py

The runner gives every run record, as it is written, the fields of outcomes.classify:

  outcome         ok, uncertified, wrong, wrong (uncertified), unknown, unsupported, timeout,
                  oom, error, harness_error, invalid_point
  stage           generate, decide, certificate, lean_export, lean_check (ArchytasZX), prepare
                  (a rival's input, in the worker), rival (the rival's own call); none when a
                  killed worker had not announced one
  cause           a short stable code (below)
  cause_message   the message behind the code, at most 300 characters
  raw_outcome     the outcome before classification, when classify replaced it

  ok, uncertified    the expected verdict, certified or not; cause verdict.VERDICT
  wrong              the opposite verdict (wrong (uncertified) when uncertified); cause
                     verdict.VERDICT
  unknown            no verdict. ArchytasZX: unknown.RUNG.STOP, the last rung note of the decide
                     reason (decide's rungs field holds every note's code, read from the whole
                     reason); a rival: rival.no_verdict
  unsupported        unsupported.CODE, the UNSUPPORTED code of the reason, set where the record
                     is made (unsupported_code)
  timeout            limit.stage_cpu (a stage's CPU limit), limit.rival_cpu, limit.rival_wall,
                     kill.stage_timer (the runner's wall timer killed the worker)
  oom                kill.sigkill (SIGKILL or exit 137), kill.cgroup_oom_kill (a rise of the
                     systemd scope's memory.events oom_kill counter, reported by the worker on
                     the scope's SIGTERM), memory.error (MemoryError in the worker),
                     memory.rival, memory.lean
  error              the tool failed: rival.exception (a driver traceback whose frame is the
                     rival's library or a driver line calling the rival), rival.exit (a binary or
                     driver exiting nonzero without a traceback), engine.load_refused (a load
                     line of the script failed), engine.exception (another exception in an
                     ArchytasZX stage), lean.rejected, kill.exit (a worker that died otherwise)
  harness_error      the harness failed, by the frame the exception came from: harness.spec_bound
                     (the engine's loader refused a rival's specification script, reason "spec
                     bound: MESSAGE"; a rival's specification is loaded inside
                     parser.lifted_bounds(), so only what still fails lands here; ArchytasZX's
                     own runs keep the default bounds), harness.prepare (an
                     exception in the worker while preparing a rival's input; every rival's own
                     call runs in a subprocess), harness.driver (a driver traceback whose deepest
                     driver frame is a harness helper, number, _build, _identity or add, or a
                     driver line that calls none of the rival's names), harness.generate (an
                     exception while generating the ArchytasZX script), limit.prepare_cpu
                     (a rival's preparation used up its CPU limit, section 11),
                     limit.generate_cpu (the generate stage, the harness's translator, used up its
                     CPU limit or was killed by the stage timer, unless its open span is the
                     engine's own input.*; the engine reading the script is in decide and its
                     timeout stays ArchytasZX's), kill.generate_oom (a memory kill whose open span
                     is generate.script, the span around the translator, and not under input.*;
                     a record without spans keeps its oom)
  invalid_point      a run with a verdict (ok to unknown) of an F equation whose pair is equal on
                     the run's region by benchmarks.differs.equal_at; cause pair_equal_at_point.
                     The region is the run's point for a rival; for ArchytasZX it also spans n
                     (0..64) unless the circuit is unrolled or has no size parameter, and d
                     (1..64) unless the script is literal in d, since decide settles the family
                     at a bound count and dimension. A failure there keeps its outcome and is
                     flagged point_invalid. equal_at is None, not
                     equal, for an F record whose
                     witness pairs a pure boundary with the same boundary doubled.

The rung stop codes are the engine's Decision.stops, one (rung, code) per rung tried in ladder
order, written RUNG.CODE (outcomes.stop_codes): normal_form.agree, .differ; oracle.mismatch,
.none_evaluated, .refused, .no_mismatch; saturation.merged, .saturated, .iteration_limit,
.enode_limit, .application_limit; symbolic.equal, .differ, .entries_differ, .indeterminate,
.indeterminate.replicated_factors, .declined.box_meets_wire, .declined.scalar_budget,
.declined.other; path_sum.equal, .unequal, .residual, .not_applicable; induction.proved,
.refuted, .base_not_proved, .step_not_discharged and the same under induction_reversed;
proof.no_proof and refutation.no_lean from certification; the stops after ("doubled",
"doubled") prefixed doubled., another doubled stop written doubled.CODE. A record written before
Decision.stops existed has its codes read from the decide reason's "; "-separated notes (RUNGS):
the same codes where a note matches, RUNG.other where none does, RUNG.truncated for the last
note of a reason cut at 400 characters, notes after an induction note (its base case's own
decision) not read.

Aggregates read the codes, never the messages; harness_error and invalid_point points, and runs
flagged point_invalid, are left out of the counts' points (harness_error and invalid_point have
their own columns), and causes.* counts points per tool, version, set, outcome, stage and cause.

    python -m benchmarks.reclassify RAW_DIR FALSE_SET OUT_JSONL [--journal]

re-reads logged records without re-running them and writes them, classified afresh, to OUT_JSONL
(outside RAW_DIR, which it never writes), printing the outcome counts per tool before and after.
--journal maps a worker that died with exit 143 to oom (kill.cgroup_oom_kill) when the user
journal has a scope's "Failed with result 'oom-kill'" from 10 s before to 2 s after the record's
finish time; records written before the worker reported its oom_kill rise need it. aggregate
applies the same journal test to every record, and the runner, when a worker in a scope ends
with exit 143 and no kill source, waits up to 3 s for its own scope's (run-p<pid>-*) OOM-kill
journal entry and records the kill as cgroup oom_kill. reclassify also recomputes an adapter's
logged result through its rederive hook (published_proofs: the verdict from its files) and a
CHECK_ONCE tool's units (K = 1, one success when a run of the unit is ok), and prints the units
with K reached before and after.


11. TOOLS
---------

Implementation: benchmarks/tools/ (one adapter per tool: supports, run), drivers in
benchmarks/tools/drivers/, environments in benchmarks/.venvs/ (Python 3.12, one per tool)

Every tool follows the same points, limits and repeats. Rival preparation (the expanded circuit,
QASM through Qiskit, the specification as a dense tensor or a ZX graph) is the stage prepare: it
is not part of the measured check time but runs under a CPU limit of its own
(stages.prepare_timeout_seconds when set, else stages.timeout_seconds), a profiling timer that
re-fires until it escapes. The timer pauses during each driver or binary call and resumes with
the budget left after it, so every CPU second the worker itself spends counts against one budget
and the rival's own processes none. A preparation over its limit is the harness's cost, not the
rival's: a harness_error in stage prepare (cause limit.prepare_cpu), and the rival is not called
again. The tool's
own work runs in its own environment and is the timed check stage. Unsupported instances are
recorded with the reason and counted. Every QASM angle is written as p*pi/q when angle/pi has a
continued-fraction convergent p/q within 2^-50 relative with |p| and q below 2^63 (the integer
range of the QuiZX and QCEC readers), else as a fixed-point decimal; no angle carries an exponent.
A dense specification or Cirq simulation with more than 64 tensor axes (numpy's limit) is
unsupported, checked before any entry count, since at d = 1 the entry count stays 1.

13. TESTS
---------

The suite's pass/fail checks are scripts (never pytest):

    python -m tests._bench_subjects_script [GLOB ...]   1: every naive circuit equals its
                                                        specification at n <= 3, d <= 4 by the
                                                        oracle, and the dense IR semantics
    python -m tests._bench_suite_script false           2: witnesses and equal-where claims
    python -m tests._bench_suite_script rivals          3: rival translations, each run in
                                                        a child process; a run killed by a
                                                        signal or an abort is a SKIP line
    python -m tests._bench_suite_script schedule        4: the point schedule
    python -m tests._bench_suite_script stats           5: the median interval
    python -m tests._bench_suite_script resume          6: kill, resume, rerun
    python -m tests._bench_suite_script trace           7: tracing off equals on; nesting

tests/_trust_mutations_script.py (the Lean mutation table) uses tests/trust_helpers.py.


14. ESTIMATED RUN TIMES
-----------------------

A unit costs about (K + 1) x runs x (decide + certificate + export + Lean check) for its
successes plus the failures that end phase 1 and phase 2, each failure up to the stage limits.
On the development laptop (8 threads, 4 workers) a successful sample point takes 0.1 to 20 s to
decide and 10 to 230 s to check in Lean (shor_code, symbolic: 226 s), so a fully successful
ArchytasZX unit takes about 17 x 3 x 1.5 min = 75 min; a failure by timeout costs up to
timeout_seconds per stage. The default limits are twice the longest successful stage expected:
one hour per stage (decide up to about 30 min, Lean up to about 15 min, SQIR's Teleport.v about
20 min), 120 s per witness probe and 1800 s per equation for the F search. The run is bounded by
the failures, not the successes: count one limit per unit (ArchytasZX and each rival) divided by
the workers; for a quicker laptop pass, lower stages.timeout_seconds (for example 600).

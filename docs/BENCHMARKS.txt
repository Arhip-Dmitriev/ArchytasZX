ARCHYTASZX DOCUMENTATION
========================

The Benchmark Suite, Version 2

Applies to: ArchytasZX 2.0.x
Implementation: benchmarks/ (python -m benchmarks), archytaszx/trace.py (timing spans)


1. PURPOSE
----------

The suite measures how far, how fast and with how large a proof the engine settles the
equations "circuit = what the circuit is supposed to do", true ones (the set S) and adversarial
false ones (the set F), against the tools a user would otherwise reach for. It reports
quantities: times, counts, sizes and rates. Pass/fail checks of the suite are tests (section
13). Every ArchytasZX result comes from symbolic rewriting; the numeric oracle enters only where
the engine itself uses it. Rival tools run as their users run them, simulators included.

Everything that defines a run comes from one file, benchmarks/config.toml; every value can be
overridden on the command line with --set KEY=VALUE, and every run is keyed by the hash of the
resolved configuration (section 10).


2. TERMS
--------

  Term         Meaning
  -----------  ---------------------------------------------------------------------------
  equation     a pair of diagrams claimed equal: the naive circuit and the specification
  subject      a named algorithm, code, protocol or circuit; it gives one or more equations
  S, F         the true equations; one false equation per equation of S
  version      symbolic (n and d letters), concrete (n and d numbers), restricted (a claim
               limited by engine clauses)
  point        one concrete (n, d) of one equation
  run          one tool on one point (or the symbolic version), in a fresh process
  stage        one timed part of a run: generate, decide, certificate, lean_export, lean_check
               (ArchytasZX); prepare and check (rivals)
  unit         one (equation, tool): its symbolic run, phase 1 ladder and phase 2 fill
  K            the successful points each unit aims for (default 16)


3. THE SUBJECT CATALOGUE
------------------------

Implementation: benchmarks/subject.py, benchmarks/subjects/*.py, benchmarks/ir.py,
benchmarks/translate.py

3.1 Subject files

One Python file per subject in benchmarks/subjects/ defines SUBJECT, a Subject:

  Field           Meaning
  --------------  -------------------------------------------------------------------------
  id, name        identity; id equals the file name
  category        algorithm, code, protocol or circuit
  source          a key of public_publications/references/REFERENCES.bib or a
                  citation
  size_parameter  what n counts (qudits, code distance, ...), or None for a fixed size
  dimension       "general" (any d in the domain) or a fixed int (2 for qubit subjects)
  domain          Domain(n_min, n_max, n_step, d_min, d_max, d_condition), the condition one
                  of any, ge2, prime, odd, odd_prime, even
  equations       Equation(key, circuit, specification, form, reference, literal)
  restricted      tuples of engine clauses (n = v, n >= c, n = a*m + c, d = v, d >= c); each
                  tuple is an equation of its own, with its own F partner
  clifford, note  a flag and a remark, not read by the suite

An Equation's circuit maps (n, d) to an IR circuit; its specification maps a SpecContext to a
ZXW diagram body in the engine's DSL, written from the definition and independent of the
circuit. form says how n enters: boxed (a register count, so the symbolic version exists),
unrolled (one wire per qudit, concrete n only) or fixed. literal writes every dimension as a
literal (phase tables need it). reference, when given, is a gate-level IR circuit realising
the specification (a textbook alternative: a CX ladder for a fan, the plain gate for a gate
identity); tools that compare two circuits use it. Without one, QCEC uses the specification as
one dense Unitary or Prepare gate (benchmarks/tools/rival.py, reference_circuit); Feynman, DiZX
and AutoQ need an explicit reference. Test 1 checks every reference against the specification.

3.2 The circuit IR

Wires are names; a register is a name with a count (int or symbol), and a gate naming a register
acts on every copy. Gates: Init, Post, Discard, Measure; X^a (|k> -> |k+a>), Z^a
(|k> -> w^(ak)|k>), F^p; ZPhase and XPhase (phase entries or a rule in k); CX and CZ (s = +1 or
-1); Swap; PhaseFn (a diagonal phase function of several wires); MCX and MCZ (controls on given
values); Perm (a permutation of the joint basis); Oracle (|x, y> -> |x, y + f(x)>). A
classically controlled correction is a CX or CZ from a measured wire. Amounts and rules are
sympy expressions in d, n and k.

3.3 The naive translator

translate.translate turns an IR circuit into a DSL body, one generator group per gate, every node
named and every wire explicit, no simplification, deterministic output. Encodings (D the wire
dimension):

  Gate          Diagram                                                   Scalar
  ------------  --------------------------------------------------------  ---------
  Init v        X(0 -> 1) phase{k: -v k/D}                                D^(-1/2)
  Post v        X(1 -> 0) phase{k: v k/D}                                 D^(-1/2)
  Discard       G(1 -> 0)
  Measure       Z(1 -> 2), second output to G
  X a, Z a      X(1 -> 1) phase{k: -a k/D}, Z(1 -> 1) phase{k: a k/D}
  F p           p mod 4 F nodes
  CX s          Z(1 -> 2) on c, X(2 -> 1) on t, joined (F F when s = -1)    D^(1/2)
  CZ s          Z(1 -> 2) on c, Z(2 -> 1) on t, joined by F (F^3 when -1)   D^(1/2)
  PhaseFn       binders to one leg, Z with the phase table, splitters       e^(2 pi i f(0))
                back; the phase at index 0 moves to the scalar
  MCZ, MCX      PhaseFn on controls and target (MCX between F and F^3)
  Oracle        F, PhaseFn f(x) y / D, F^3 on y
  Perm          fresh Z(0 -> 1) leg t, PhaseFn -t p(x)/D on (t, x),          D^(-1/2)
                Z(1 -> 0) on x, F on t

A register's gates go in one node-scope box per count; a gate between a register and a single
wire leaves the single wire's spider outside the box, where it takes one leg per copy. Phase
tables, multi-controlled gates, oracles and permutations need literal concrete dimensions; the
symbolic version of such an equation is unsupported and recorded as such.

3.4 The engine script

subject.script builds, for one equation at one version,

    @rhs =
        dim d [= V]          (general d, not literal)
        count n [= V]        (boxed n)
        SPECIFICATION
    load
        dim d [= V]
        count n [= V]
        NAIVE CIRCUIT
    decide against @rhs [for CLAUSES]

A concrete point binds the numerals as a user writing numbers does; the engine abstracts them
on entry (ENGINE_COMMANDS.txt, section 3), so the claim decided is the family's, the bound
values reported beside it. Literal dimensions and unrolled counts are instances.

4. THE FALSE SET
----------------

Implementation: benchmarks/breaks.py; generated into results/false_set.json

Every S equation gets one false partner: one break applied to its circuit IR (the specification
is never edited, so every tool sees the same pair). The kind is picked per equation by the
assignment rule (round_robin from the equation's index, or a seeded shuffle); a kind with no
variant that yields a witness is skipped for the next. Each F record stores the edit, a witness
(a point, output and input indices, both values; for a mixed equation, indices of the doubled
diagram) and where the pair stays equal.

  Kind                    Edit                                              Equal where
  ----------------------  ------------------------------------------------  -------------------
  beyond_oracle           phase k (d-1)(d-2)(d-3)(d-4)/d, or a C(n,4)/d      the oracle grid
                          phase on a boxed equation, on an output wire       (d <= 4, n <= 3)
  beyond_N                unrolled: X on an output when n > N; boxed: a      n <= N
                          counting gadget of dimension N + 2 giving -1 at
                          n = N + 1 (mod N + 2); rivals see the same sign
  prime_only              phase (k^d - k)/d                                  prime d (and the
                                                                             Carmichael numbers)
  qubit_only              the antipode F^2 on an output                      d <= 2
  coincident_dims         phase k (D1 - D2)/D1                               D1 = D2
  scalar_small_one        scalar 1 + (d-1)(d-2)(d-3)(d-4), or 1 + n..(n-3)   the oracle grid
  global_phase            scalar e^(2 pi i/7)                                up to a global phase
  tiny_phase              phase 1/d^k (k = tiny_k) at index 1               nowhere
  leg_order               a swap of two wires of one register copy, or of    nowhere
                          the last two outputs
  box_boundary            scalar 1 + 0^(n - n_min)                           n > n_min
  state_not_map           Z at the start of an input wire                    on input 0
  single_entry            a phase table: -1 where every output is 1          elsewhere
  wrong_phase             one phase or amount changed                        nowhere
  missing_gate            one gate dropped                                   nowhere
  extra_gate              X appended on an output                            nowhere
  swapped_control_target  one CX reversed                                    nowhere
  off_by_one_n            the circuit at n + 1                               nowhere
  wrong_dimension         one wire's dimension + 1                           nowhere

Witnesses are found densely when the tensor has at most 2^18 entries, else by plugging basis
states and effects into the closed diagram (nodes of at most 12 legs) or by symbolic contraction
at the bound values. The boxed beyond_N witness is factored: a nonzero specification entry e at
n = N + 1 (symbolic contraction) and the gadget's value g there, the broken entry being g e; the
gadget's closed form is tested at N = 1, 2, 3 (section 13). F has the same three versions as S.
Kinds tiny_phase and single_entry raise the F equation's d floor to 2.

The search is bounded in time: one probe (one point of one variant) gets
false_set.probe_seconds, and an overrun counts as no witness at that point; one equation gets
false_set.equation_seconds over all its kinds, and an overrun ends the search with no F partner,
recorded with reason "time budget"; an equation whose every probe overflows the oracle's
contraction cap has none either, with reason "oracle size". The large fixed codes golay_code,
tesseract_code and polynomial_code have no F partner. On an unrolled equation a break that names
a wire records its role (open outputs, inputs, all wires) and position, and is applied to the
wire in that position at each n. Test 2 reports both reasons, and oracle-size overflows of its
equal-where checks, as SKIP lines.


5. POINTS
---------

Implementation: benchmarks/points.py

Each unit has its own seed, derived from (points.seed, equation, tool). A draw takes u uniform
on [0, 1) independently for n and d: d = floor((d_max + 1)^u), n = floor((n_max + 1)^u) - 1;
out-of-domain values are redrawn; an axis the subject lacks is held at its fixed value.

Phase 1, the ladder: step k = 1..K at n_k = floor((n_max + 1)^(k/K)) - 1 and
d_k = floor((d_max + 1)^(k/K)), clamped to the range, moved up to the nearest domain point and,
when already used, to the next unused one (n raised first, then d). Steps run in order; the
first failure (timeout, error, out of memory, wrong or unknown result, unsupported) ends the
ladder and is recorded.

Phase 2, the fill: draws are kept when not at least as large, in both n and d, as some failed
point, and not used before. A success counts toward K; a failure joins the failed points. The
fill stops at K successes, at phase2_extra_failures failures, or when the draws run out; the
last two record region_exhausted. A domain of fewer than K points is run whole.

The symbolic version is one more run outside K. A restricted equation draws from its restricted
domain.


6. BENCHMARKS
-------------

B1, proving S, and B2, refuting F, record per run every stage's CPU and wall seconds and peak
memory, the derivation steps, kernel inferences (per kind), certificate bytes (the text of
certificate show), Lean lines and bytes, Lean check CPU and per-declaration profiler
milliseconds, the axiom class, and the span tree (section 7); per unit, the frontier, K reached
and region_exhausted. B2 adds the counterexample point and the Lean refutation's size. A run is
successful when stage decide gives the expected verdict (equal for S, unequal for F); a run
giving the opposite verdict is logged wrong.

B3, diagram size (benchmarks/size.py): for every successful ArchytasZX B1 run, the smallest
diagram over both sides, both normal forms and every diagram of every certificate (replayed
step by step): nodes per generator (Z, X, W, F, T, Ti, B, S, G), node- and port-scope boxes and
their deepest nesting, phase entries, weight entries, wires, self-loops, inputs, outputs and the
scalar's operation count; total = nodes + boxes + phases + weights + wires, ties broken by fewer
wires. The same counts of the naive circuit and the naive / smallest ratio are reported. PyZX
and QuiZX report vertices and edges of their reduced graph; tket reports gates and two-qubit
gates after FullPeepholeOptimise.

  contraction, .counterexample_     reversed) and the three restriction steps
  search, .induction, .induction.
  base, .induction.step,
  .restriction.family, .restriction.
  substitute, .restriction.pair
  saturation.iteration              rewrite/egraph.py, labelled by the iteration number
  rewrite.match, rewrite.apply      rewrite/engine.py, labelled by the rule

8. STAGES OF AN ARCHYTASZX RUN
------------------------------

Implementation: benchmarks/tools/archytaszx.py, benchmarks/stages.py

  Stage        What runs
  -----------  -----------------------------------------------------------------------------
  generate     the engine script built from the subject (translation of the circuit)
  decide       every line of the script in one fresh session, concrete axioms on
  certificate  certificate kernel: the proof object built and kernel-checked
  lean_export  certificate lean FILE
  lean_check   the Lean runner on FILE with #print axioms; class clean, unproved, opaque

Each stage has its own CPU limit (stages.timeout_seconds, default one day), enforced by a
profiling timer that re-fires until it escapes the engine; the worker is killed after wall_factor
times the sum of its stage limits. A stage that cannot run (certificate and Lean after an
unknown verdict) is recorded not_run. Only decide decides success; later stages are recorded
with their status.


9. STATISTICS
-------------

Implementation: benchmarks/stats.py

Laptop: exactly repeats.laptop.runs runs (3) of every successful point. Cluster: at least
min_runs (5), then until the 99 % confidence interval of the median decide CPU has half-width
within precision (5 %) of the median, or max_runs (30). The interval is the exact order-statistic
interval: the largest j with 2 P(Binomial(m, 1/2) <= j - 1) <= 1 - confidence gives
[x_(j), x_(m+1-j)]; at 99 % it exists from m = 8. Points reaching max_runs are noisy; a point is
decided by its first run, and a later failing repeat makes it unstable. Every aggregate row has
the median, quartiles, minimum, maximum, the interval, the number of runs and the raw values.


10. EXECUTION
-------------

Implementation: benchmarks/runner.py, benchmarks/worker.py, benchmarks/log.py,
benchmarks/slurm.py

10.1 The runner

    python -m benchmarks run [--profile laptop|cluster] [--set KEY=VALUE ...] [--shard I/N]
                             [--only EQUATION|TOOL-GLOB ...]
    python -m benchmarks false [--set KEY=VALUE ...]      generate results/false_set.json
    python -m benchmarks list [--set KEY=VALUE ...]       the S equations, one per line,
                                                          with category and whether the
                                                          symbolic version exists

Every action also takes --config PATH, a configuration file in place of
benchmarks/config.toml.

Units run platform.jobs at a time; a unit's runs go in order. Every run is a fresh worker process
(python -m benchmarks.worker) under a memory cap of memory_fraction of the available memory
divided by the workers (a systemd scope without swap, else a soft RLIMIT_AS, which Lean and
the Quantomatic JVM lift: they are bounded by the Lean slots and -Xmx2g). The worker announces each
stage, so a killed run records the stage it died in.

10.2 Log and resume

Each finished run is appended at once, with flush and fsync, as one JSON line to
results/raw/HOST-JOB-TASK-wK.jsonl, one file per worker thread; lines are never edited. A run is
keyed by (config hash, equation, version, tool, point, repeat, trace). On start every log is read
and every key present is reused: the schedule replays from logged outcomes, and a unit whose
unit record exists is skipped. A run cut off before its line was written leaves nothing and is
re-run whole; a truncated last line is ignored. SIGINT or SIGTERM stops new runs and kills
running workers, whose runs are re-run on resume. Aggregates and plots come only from the logs.

10.3 Cluster (Zaratan)

    python -m benchmarks slurm [--set KEY=VALUE ...]      writes benchmarks/slurm/run.sbatch

The job array runs on the scavenger partition only, with --requeue, whole cores
(--cpus-per-task = slurm.cpus_per_task, --hint=nomultithread) and one worker per core; array
task i runs shard i of the units. Each job first runs the calibration script (GHZ, symbolic
decide) three times; its median CPU is stored with every run and in the job's environment
record, which also holds the node, CPU model, frequency governor and memory. Reports give times
scaled by the calibration beside the raw times; raw times are compared within one CPU model.

10.4 Memory

Lean runs in a systemd scope of its own capped at memory_fraction of the total memory, outside
the worker's scope (whose cap would evict the memory-mapped Mathlib files). At most
floor(0.85 x total memory / 7000 MiB) checks run at a time across workers (one Lean check peaks
near 6.7 GiB), between 1 and 5; BENCH_LEAN_SLOTS overrides. Peak memory is recorded per stage.

10.5 Laptop

The same runner and log with the laptop profile; interruption and resume as in 10.2.

                          Deutsch-Jozsa, Grover, QPE, superdense coding, teleportation, GHZ, the
                          three- and nine-qubit codes; VyZX: Bell state, teleportation, three-CNOT
                          SWAP), timed, with proof lines and bytes; CoqQ and QBricks fetched

Every rival is built by benchmarks/tools/setup_rivals.sh (pinned commits and versions); until
then each instance is recorded unsupported with "not installed". The Coq toolchain and the
proof projects live under BENCH_COQ_HOME (default ~/.cache/archytaszx-bench/coq): Coq's dune
build rejects paths with non-ASCII characters.

Channels (measurement, discard) are unsupported for every rival.

14. ESTIMATED RUN TIMES
-----------------------

A unit costs about (K + 1) x runs x (decide + certificate + export + Lean check) for its
successes plus the failures that end phase 1 and phase 2, each failure up to the stage limits.
On the development laptop (8 threads, 4 workers) a successful sample point takes 0.1 to 20 s to
decide and about 60 s to check in Lean, so a fully successful ArchytasZX unit takes about
17 x 3 x 1.5 min = 75 min; a failure by timeout costs up to timeout_seconds per stage. With the
default one-day limit the laptop run is bounded by the failures, not the successes: count one
limit per unit (ArchytasZX and each rival) divided by the workers. For a laptop pass, lower
stages.timeout_seconds (for example 600) and repeat with the default limits on the cluster,
where the job array spreads the units over its cores.
